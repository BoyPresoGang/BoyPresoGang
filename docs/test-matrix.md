# Week 10 Manual QA Test Matrix

This matrix lists the current user-facing features and important API/CRUD flows. Execute each scenario manually and record the result during QA; no scenarios are pre-marked as passed or failed.

## Customers

| Feature | Happy | Boundary | Invalid | Empty | Permissions |
|---|---|---|---|---|---|
| Customer list | Load current records from `GET /api/customers`; verify ID, name, and contact number. | Verify one record and many records. | Verify human-readable 500/network error and retry behavior. | Verify the empty-list state when no customers exist. | List access should remain available; verify no unauthorized action is exposed. |
| Create customer | Create with a valid name and exactly 11-digit contact number; verify success feedback and list navigation. | Test name length limits and exactly 11 digits. | Test missing fields, short/long name, non-numeric contact, and incorrect contact length; verify 422 inline feedback. | Submit with all fields empty and verify validation feedback. | No delete authorization is involved; verify normal create remains available. |
| Customer detail | Load a valid `/customers/{id}` and verify current data, Edit, and Back links. | Verify the first and a later customer ID. | Test nonexistent ID, API/server failure, network failure, and retry. | Not applicable to a valid detail record; verify the error state for missing data. | Verify detail does not expose unauthorized destructive actions. |
| Edit customer | Load `/customers/edit/{id}`, update valid data, and verify the matching customer changes. | Test name limits and exactly 11-digit contact. | Test malformed/nonexistent ID, invalid fields, and 422 handling. | Submit cleared fields and verify validation feedback. | Verify edit does not require the simulated delete role. |
| Delete customer | Confirm deletion of an existing customer and verify list refresh. | Delete the only customer and verify the empty state. | Test nonexistent customer, 500, and network failure; verify confirmation and error feedback. | Verify the list after deleting its final record. | Send `X-User-Role: admin` and verify success; missing/incorrect role returns 403. |

## System-level and cross-feature flows

| Feature | Happy | Boundary | Invalid | Empty | Permissions |
|---|---|---|---|---|---|
| Navigation | Verify list/create/detail/edit/back links use the correct resource and record ID. | Test first and later record IDs. | Verify no normal Back/Edit action uses an unintended `href="#"`; retry controls remain functional. | Verify navigation from empty and error states where available. | Navigation should not bypass resource authorization. |
| Async feedback consistency | Verify loading, success, and post-action refresh feedback for each resource. | Test slow responses and action followed by list refresh. | Test 403, 404, 422, 500, network, and malformed/non-200 responses; messages must be human-readable. | Verify list, dropdown, and detail empty states. | Verify permission failures remain distinct from validation/server failures. |
| Demo authorization mechanism | Verify authorized customer, product, order, and delivery actions work through the frontend. | Test each supported action once with its expected header. | Remove or alter headers and verify the existing 403 feedback. | Not applicable. | Customer delete: `X-User-Role: admin`; Product delete: `manager`; Order cancel: matching `X-User-Id`; Delivery cancel: `dispatcher`. |
| Order stock lifecycle | Create an order and verify stock decreases; update quantity/product and verify stock is adjusted safely; cancel and verify restoration. | Test exact stock, zero stock, same product, product switch, and multiple orders. | Test over-stock, failed create/update, missing product, and repeated cancellation; stock must not become negative or restore twice. | Verify unavailable products cannot be selected for additional quantity. | Verify stock-changing operations retain their existing authorization rules. |
| Order–Delivery lifecycle | Create an order, create one eligible delivery, then cancel it and verify the order becomes eligible again. | Test active, delivered, and cancelled delivery statuses. | Attempt duplicate active delivery and invalid order/date/status. | Verify no eligible orders when all orders have active deliveries. | Verify delivery cancellation still requires dispatcher authorization. |
| Atomicity and concurrency | Verify successful order/delivery operations update related records consistently. | Submit competing stock-consuming or delivery-creating requests where feasible. | Verify failed operations do not partially change stock or create duplicate active deliveries. | Verify consistent state after failed refreshes or failed follow-up requests. | Verify backend checks remain effective even when UI restrictions are bypassed. |
| API/CRUD contract | Verify successful list/create/show/update/delete responses and refreshed UI state. | Test one record, final record, and repeated valid operations. | Verify standardized 422 field errors, 403 authorization errors, 404 not-found responses, and 500/network handling. | Verify empty collections and missing relationships are handled clearly. | Verify authorization headers are only supplied for the intended destructive actions. |
